# AGENTS.md

Канонические правила ИИ-кодинга для проекта «Греческая читалка Нового Завета»
(репозиторий `ru2agr_reading`).

Codex, Claude Code, Cursor, Gemini CLI, GitHub Copilot и другие ИИ-инструменты
обязаны прочитать этот файл и следовать ему до любого изменения кода.
Инструмент-специфичные файлы (`CLAUDE.md`, `GEMINI.md`,
`.cursor/rules/project.mdc`, `.github/copilot-instructions.md`) — мостики,
указывающие сюда; этот файл — единственный источник правды о **правилах
работы**.

Источник правды о **продукте, архитектуре и плане работ** —
[DEVELOPMENT.md](DEVELOPMENT.md): раздел 3 — целевая архитектура, раздел 4 —
функциональная спецификация, раздел 5 — задачи (выполняются последовательно,
сверху вниз), раздел 6 — глобальный Definition of Done, раздел 7 — бэклог,
который без отдельного решения не делается.

## Контроль качества (реальность)

Git-хуков, CI и линтеров в репозитории нет. Единственная страховка — то, что
ты запускаешь сам.

Пока `package.json` не создан (задача 0.1 ещё не выполнена), проверка только
ручная — статический сервер и браузер:

```bash
npx serve .          # или python3 -m http.server
```

Начиная с задачи 0.1 (Vite + Vitest):

```bash
npm test             # Vitest — после каждого изменения движка/стора/данных
npm run dev          # ручная проверка фичи в браузере
npm run build        # полный гейт: перед «готово» и перед коммитом
```

Никогда не отчитывайся «задача готова» с красными тестами, сломанной сборкой
или непройденной ручной проверкой из чеклиста задачи. Не добавляй CI,
git-хуки, линтеры, Prettier или другие тест-фреймворки по собственной
инициативе — сначала предложи.

## Что это за проект

Спокойная библейская читалка Нового Завета (PWA, offline-first) с регулируемым
греческим слоем: пользователь читает Синодальный перевод, а греческий
постепенно «просвечивает» в тексте — сначала буквы, потом слова из личного
словаря, потом реальные формы оригинала (режимы 1–5, см. DEVELOPMENT.md 3.4).

Текущее состояние кода — прототип буквенного слоя: конвертер «русский текст →
текст с греческими буквами» (`text-converter.js`, `config.js`, `ui.js`,
`storage.js`, `sw.js`, `index.html`, `styles.css`). Судьба каждого файла
расписана в DEVELOPMENT.md раздел 2 — не удаляй, не переноси и не
переписывай их раньше той задачи, которая это предписывает.

## Стек

- Vanilla JS (ES-модули). Никаких фреймворков: React/Vue/Svelte и любые
  state-менеджеры запрещены — стор это свой pub/sub (`src/state/store.js`).
- Сборка: Vite + vite-plugin-pwa (появляются в задачах 0.1 и 1.8). Пакетный
  менеджер — `npm`. Node 20+ для скриптов пайплайна в `tools/`.
- Тесты: Vitest — только для чистых модулей (движок `src/engine/**`, стор,
  валидация данных). UI тестируется руками по чеклисту задачи.
- Состояние пользователя: IndexedDB (база `ru2agr_db`, store `app_state`)
  через единственную обёртку — сейчас `storage.js`, после задачи 0.1
  `src/storage/db.js`. Никаких бэкендов, аккаунтов и серверного состояния.
- Данные: статические JSON в `data/`, генерируются Node-скриптами из
  `tools/` и коммитятся. Сырые исходники — в `tools/sources/` (в .gitignore).
- Стили: чистый CSS с custom properties (токены ролей, см. DEVELOPMENT.md
  4.9). Без Tailwind, CSS modules, CSS-in-JS и UI-библиотек.

Зависимостей почти нет, и это сознательно. Ответ по умолчанию на «добавить
пакет?» — нет; devDependencies ограничены `vite`, `vite-plugin-pwa`, `vitest`.

## Жёсткие ограничения

- НИКОГДА не используй `Math.random()` (и любую недетерминированную
  случайность) в движке. Один и тот же текст + одни настройки → один
  результат: вероятность замены считается через `hash01(seed)` от позиции
  (DEVELOPMENT.md 3.1 п. 3 и 3.4).
- НИКОГДА не тяни DOM, `fetch`, IndexedDB или глобальное состояние в
  `src/engine/**`. Движок — чистые функции «текст + настройки → `Segment[]`»,
  покрытые тестами; рендерит сегменты только `src/ui/render.js`.
- НИКОГДА не обращайся к `indexedDB`/`localStorage` напрямую из UI-кода.
  Только через обёртку хранилища; каждое обращение — fail-soft (try/catch,
  приложение продолжает работать без хранилища).
- НИКОГДА не редактируй руками сгенерированные данные `data/bibles/**` и
  `data/lexicon/forms.json` — меняй скрипт в `tools/` и перегенерируй
  (`npm run build:data`). Курируемые руками файлы: `data/alphabet.json`,
  `data/lexicon/core.json`.
- НИКОГДА не коммить текстовые данные без проверки лицензии источника
  (DEVELOPMENT.md 3.5). Сомнительная лицензия — остановись и спроси.
  `tools/sources/` в git не попадает.
- НИКОГДА не добавляй аналитику, телеметрию, error-reporting SDK или любое
  удалённое логирование. Приложение полностью локальное и оффлайн-первое.
- НИКОГДА не добавляй «умную» адаптацию обучения (подсчёт кликов, скрытые
  метрики, автоподбор сложности). Управление обучением — только ручное
  (DEVELOPMENT.md 3.1 п. 7).
- Полный перерендер глав — только когда меняется картина замен; статусы и
  подсветка — точечные мутации классов без сноса DOM (DEVELOPMENT.md 3.1
  п. 8). Не нарушай эту политику «для простоты».
- Весь видимый пользователю текст — по-русски. i18n-фреймворк не вводится.
- DO NOT затевать широкие рефакторинги при решении узкой задачи. Известный
  долг остаётся, пока задача не про него.

## Правила работы

1. Перед задачей прочитай разделы 3–4 DEVELOPMENT.md; задачи раздела 5
   выполняются последовательно, не перепрыгивай и не объединяй.
2. Чеклист задачи — обязательная часть Definition of Done. После выполнения
   отметь её чекбоксы `- [x]` в DEVELOPMENT.md тем же коммитом.
3. Один коммит на задачу; сообщение — из промпта задачи (conventional
   commits: `feat: …`, `docs: …`).
4. Работай в ветке `dev*`; в `main` — только через PR/merge.
5. Будь консервативен при изменении: имени базы и ключей IndexedDB
   (`ru2agr_db` / `app_state`, ключи `settings`, `progress`, `dictionary` —
   у пользователей уже есть данные), схем JSON из DEVELOPMENT.md 3.3,
   контракта `Segment`, сигнатур движка (`composeVerse`, `applyLetterLayer`…),
   hash-маршрутов.

## Стиль кода

- ES-модули, named exports, маленькие однозадачные файлы (один модуль — одна
  забота: hash, rules, storage, loader…).
- Чистая логика (замены, хеши, морфология, сортировки) живёт в `src/engine/`
  и `src/state/`, где её можно тестировать без DOM.
- Экран UI — модуль с интерфейсом `mount(container, ctx)` / `unmount()`;
  компоненты не лезут в хранилище напрямую, работают через стор.
- Форматирование: 2 пробела, точки с запятой; кавычки и идиомы — как в
  окружающем коде. Не переформатируй нетронутые файлы.
- Доступность — требования из DEVELOPMENT.md раздел 6: интерактивные span'ы
  достижимы с клавиатуры, aria-атрибуты на карточках/шторках, touch targets
  ≥ 44px, видимый `:focus-visible`, контраст ≥ 4.5:1.

## После изменения кода

- Движок/стор/данные менялись → `npm test` зелёный (когда тесты уже есть).
- UI менялся → ручная проверка на мобильной (375px) и десктопной (1280px)
  ширине, в светлой и тёмной теме, по чеклисту задачи.
- Перед «готово» и перед коммитом → `npm run build` (после задачи 0.1).
- Данные менялись → перегенерированы пайплайном, валидация скрипта прошла,
  лицензия источника проверена.

## Финальный отчёт

Всегда сообщай:

```text
Checks: какие команды/проверки выполнены (и pass/fail)
Changed files: список
DEVELOPMENT.md: какие чекбоксы отмечены, или «план не менялся»
Данные/лицензии: что перегенерировано, лицензия источника, или «не менялись»
Notes: риски, follow-up'ы, пропущенные проверки (с причиной)
Git status: clean или список оставшихся изменений
```

Не объявляй задачу выполненной, если:

- `npm test` или `npm run build` падают
- ручная проверка из чеклиста задачи не пройдена
- чекбоксы задачи в DEVELOPMENT.md не отмечены
- закоммичены данные с непроверенной лицензией или сгенерированный JSON
  правлен руками
