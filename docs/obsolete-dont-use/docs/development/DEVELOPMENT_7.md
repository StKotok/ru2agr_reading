## 1. Довести золотой эталон до ручной разметки

### 1.1. Методология

Для каждого из 43 стихов (23 dev + 20 heldout) нужна независимая ручная разметка.
**Не смотреть на текущий alignment при разметке** — иначе эталон подтвердит те же
ошибки, что допустил алгоритм.

**Источники для сверки:**

1. **Подстрочник Винокурова** — русско-греческий подстрочник Нового Завета
   (база UBS/NA, близко к SBLGNT). Основной инструмент.
2. **Аппарат NA28** — для проверки текстуальных вариантов в разночтениях.
3. **Собственное знание койне и Синодального перевода** — для краевых случаев,
   где подстрочник может расходиться с Синодальным переводом.

**Процесс на один стих:**

1. Прочитать русский текст (Синодальный) и греческий (SBLGNT-токены с леммами).
2. Для каждого русского слова определить: имеет ли оно прямой греческий эквивалент
   в этом стихе?
3. Если да — указать индекс греческого токена (0-based) и уровень качества:
   - `e` (exact) — прямое лексическое соответствие, однозначное
   - `f` (functional) — допустимое функциональное соответствие (напр., `αὐτοῦ` →
     «свой» при отсутствии отдельного «его» в стихе)
4. Если нет — отметить русское слово как orphan (добавление перевода, pro-drop,
   TR-плюс, идиоматический оборот).
5. Отметить греческие токены без русского соответствия (артикли, непереводимые
   частицы, TR-плюсы на греческой стороне).
6. Записать текстуальные примечания (TR/NA расхождения, неоднозначности).

## 4. Итерация refine-правил (Шаг 7 плана v8)

### 4.1. Когда нужна итерация

После завершения ручной разметки золотого эталона метрики измерят **истинную**
precision/recall, а не стабильность. Если precision < 98% или recall < 70% —
нужна итерация правил.

### 4.2. Процесс итерации

1. Запустить `verify-alignments.mjs` — получить список расхождений с эталоном
2. Классифицировать расхождения по паттернам:
   - False positive (мы выровняли, эталон говорит не надо)
   - False negative (эталон выровнял, мы пропустили)
   - Wrong target (мы выровняли на другой токен)
3. Для каждого паттерна — определить причину:
   - Правило refine слишком агрессивное/недостаточно агрессивное
   - Пропущенный случай в белом списке
   - Ошибка в таблице совместимости
   - Лексиконный промах
4. Исправить правило в `refine-alignments.mjs`
5. Перезапустить: `build:data → refine → verify`
6. Повторить до критерия

### 4.3. Тест на идемпотентность

`refine(refine(x)) === refine(x)` — если refine применяется дважды, результат
не меняется. Написать тест в `tests/refine.test.js`:
- Взять случайный стих
- Прогнать refine дважды
- Сравнить alignment-пары (должны быть идентичны)

### 4.4. Второй проход местоимений (Pass A2) — повышение recall

**Зачем.** Исходный отчёт зафиксировал ~2 081 невыровненное русское личное местоимение
3-го лица (категория 3). Замер текущих данных: ~2 981 русский токен с заглавной не в начале
стиха — это имена и **местоимения Божества** («Его», «Него», «Ему»), значительная часть
которых — прямой перевод невыровненного `αὐτός`. Pass A в нынешнем виде сделал лишь
53 перенаправления и почти не добавлял пар: его шаг добавления (план v8, Pass A шаг 7)
срабатывает только при условии «ровно один невыровненный `G846` И ровно один совместимый
сирота в стихе», а в повествовательном греческом `αὐτός` встречается по нескольку раз на стих —
условие почти никогда не выполняется. Это самый крупный безопасный рычаг recall, и сейчас он простаивает.

**Что делает Pass A2.** Не перенаправляет, а **добавляет** недостающие пары
местоимение↔`αὐτός`, ослабляя условие кардинальности за счёт более сильной морфологической
дизамбигуации:

1. Собрать невыровненные русские личные местоимения 3-го лица (из инвентаря `text-utils.js`,
   с признаками падеж/число/род) и невыровненные токены `G846` (с полем `c`).
2. Сопоставить их **жадно** по согласованию: падеж+число — жёстко, род — мягко (как в Pass A);
   для предложных `αὐτός` — через `PREP_TABLE` (тот же механизм, что Pass A).
3. Добавлять пару только при **морфологически однозначном** сопоставлении: для данного
   сироты ровно один `G846` проходит согласование (и наоборот). Неоднозначные случаи
   (несколько совместимых кандидатов на близкой дистанции) — **оставить сиротами**, не угадывать.
4. Защиты precision (как в Pass A): Nom-сирота — только от Nom-`αὐτός` (страховка от
   pro-drop-подлежащего); стихи из реестра TR-плюсов — пропускать.
5. Помечать `src:"a"`; `q` по каскаду → `"e"` при морфосовпадении, `"f"` при только позиционном.

**Свойства.** Идемпотентность (повторный запуск не добавляет нового); детерминизм
(порядок — по возрастанию индекса токена). Прогон в `--dry-run` с логом всех добавлений —
выборочный просмотр глазами до записи.

**Измерение.** Вывести число добавленных пар и пересчитать покрытие. Проверить выборку
добавленных пар (~50–100) против gold/слепого LLM: добавления **не должны** опускать
precision на held-out ниже критерия. Если опускают — ужесточить условие однозначности.

### 4.5. Аудит понижений q=u

**Зачем.** Pass B понизил до `q:"u"` 7 076 пар (6.5% корпуса) — они скрыты от пользователя.
Их включение подняло бы покрытие с 78.3% до 83.7%. Часть понижена верно (реальные
лексиконные промахи, истинные кросс-клаузальные ошибки), но правило B4 («классовое
несоответствие на любой дистанции») и огульное `src:"l" → "u"` подозреваются в
**избыточной агрессивности**. Ложно понижённая пара — потерянный recall, причём невидимо.

**Что делать.**

1. **Инструментировать Pass B:** каждому понижению присвоить причину
   (`r1` артикль, `r2` «свой» без леммы, `r3` `μέν`, `r4` классовое несоответствие,
   `lex` лексиконный fallback). Вывести разбивку — сколько пар понизила каждая причина.
2. **Стратифицированная выборка** ~100 пар (пропорционально причинам), ручная проверка
   (или слепой LLM): для каждой — понижение верное или ложное? Посчитать **долю ложных
   понижений по каждой причине**.
3. **Решение по причине:** высокая доля ложных → правило ослабить/уточнить (напр., B4
   «на любой дистанции» → вернуть порог дистанции; `lex → u` → различать надёжные и
   ненадёжные лексиконные совпадения). Пересчитать на gold.
4. **Промоция:** пары, признанные верными, повысить (`u → f` или `u → e`) — но только если
   это **не опускает** precision на held-out ниже критерия. Мерить precision и recall одновременно.

**Выход:** таблица «причина понижения × доля ложных»; список ослабленных правил;
восстановленное покрытие. Скрипт `scripts/audit-downgrades.mjs`.
