## Общая оценка

План логичный, хорошо структурированный, с правильным направлением (адаптер → движок → удаление адаптера). Но содержит несколько существенных проблем — от фактических ошибок до архитектурных просчётов.

---

## Критические проблемы (блокеры)

### 1. Совместимость токенизации не верифицирована, а только предположена

План (Шаг 1, риски) говорит: «Выравнивание в `syn/*.json` не трогаем». Spot-check 1 Кор 1:1 показал идентичную токенизацию (12 токенов, тот же порядок, те же surface-формы) — **но это один стих из ~7957**. MACULA verse text содержит редакторские маркеры (`⸂ Χριστοῦ Ἰησοῦ⸃`), которых нет в старом grc. Если хотя бы в одном стихе токенизация разойдётся (crasis, элизия, разная пунктуация), индексы в `alignment` перестанут указывать на правильные греческие токены, и словарный слой (режимы 3–5) начнёт подставлять не те слова.

**Нужно:** скрипт верификации, сравнивающий токен-в-токен старый и новый формат для всех 27 книг.

### 2. Strong как массив — план теряет данные

MACULA: `strong: ["3972"]` (массив строк). Старый формат: `strong: 3972` (число). План (Шаг 1, macula-adapter.js) берёт `Number(token.strong[0])`. Это ломает несколько мест:

- **Красис-формы** (κἀγώ = καί + ἐγώ = G2532 + G1473) — второй Strong-номер молча теряется. Таких токенов в НЗ немного (~50–80), но они есть (в 1 Кор не нашлось — надо проверить весь НЗ).
- **`buildWordEntries` в reading.js:616** делает `frequencyList.find(f => f.strong === strong)` — с новым `frequency.json`, где `strong` — массив, это сравнение никогда не сработает.
- **`freq-*` записи в словаре** (reading.js:616) — `lexemeId.startsWith('freq-')` и `lexemeId.replace('freq-', '')` даёт строку, которая сравнивается со `strongKey` из `freqByStrongCache`. После миграции `strongKey` будет строкой, но ключи в `freqByStrongCache` строятся из `String(item.strong)`. Если `item.strong` стал массивом, `String(["3972"])` → `"3972"` (работает случайно для одного Strong), но для multi-strong — `"3972,2532"` — сломается.

### 3. `morphology.labelRu` из MACULA имеет дефекты

Сравнение:

| Код | MACULA labelRu | formatMorphShort (текущий) |
|---|---|---|
| V-RPP-DPM | `глаг., мн. ч., перф., страд. залог, причастие, D` | `['глаг.', 'перф.', 'страд.', 'прич.', 'мн. ч.']` |
| P-1GP | `мест., род. падеж, мн. ч.` | `['личн. мест.', 'род. п.', 'мн. ч.']` |

Проблемы MACULA-декодера:
- Код наклонения `D` (повелительное) не раскодирован — сырой `D` в выдаче.
- 1-е лицо (`1GP`) потеряно в `labelRu`.
- Формат единой строки через запятую vs массив чипов — разный UI.

План (Шаг 3) предлагает заменить `formatMorphShort` на `morphology.labelRu` — это изменит внешний вид карточки и привнесёт баги.

### 4. Нет стратегии отката

Восемь последовательных шагов, каждый зависит от предыдущего. Если на шаге 3 обнаружится, что токенизация разошлась в Евангелии от Марка — откатываться придётся через git revert трёх коммитов, затрагивающих 10+ файлов. Нужны либо feature-флаги (старый/новый формат), либо независимые ветки для адаптера и формата движка.

## Структурные проблемы

### 5. План смешивает две независимые миграции

- **(A) Смена источника греческого текста** (Clear-Bible SBLGNT → MACULA SBLGNT) — затрагивает bible-loader, form-layer, compose, render, reading.
- **(B) Обогащение лексикона** (frequency.json, core.json, семантические домены) — затрагивает lexicon-loader, word-card.

Это разные операции с разными рисками. Миграция (B) может быть сделана независимо и даже до (A) — новые поля в core.json ничему не мешают. Смешение в одном плане означает, что баг в (B) блокирует развёртывание (A).

### 6. Выходной путь `build-macula.mjs` не совпадает с планом

Скрипт пишет в `assets/data/generated/macula/`. План (Шаг 4) предлагает переключить на `bibles/grc/`. Но:
- `generated/macula/books/*.json` — **плоский массив токенов**.
- `bibles/grc/*.json` — **вложенная структура** `{ chapters: [{ verses: [{ tokens }] }] }` **с полем `text`** для каждого стиха.

Это не «переключить выход», а **полная смена выходного формата**. `build-macula.mjs` придётся научить группировать токены в главы/стихи и добавлять verse text (из `verses.json`). Это дополнительные ~50 строк кода и новый код в bible-loader.

### 7. Не указана судьба `bible-loader.js` → `loadBook('grc', bookId)`

Сейчас `loadBook` загружает `bibles/grc/{bookId}.json` и возвращает `{ id, title, chapters: [{ n, verses: [{ n, text, tokens }] }] }`. После миграции формат изменится. План говорит о `loadMaculaBook()`, но не специфицирует, остаётся ли `loadBook('grc', ...)` или удаляется. Вызов `loadBook('syn', bookId)` для Синодального текста остаётся — это сбивает с толку.

## Конкретные ошибки и нестыковки

### 8. `\r` в морфокодах старого формата

Старый grc содержит `"morph": "N-NSM\r"` (carriage return из TSV). MACULA этого не имеет. При переходе на MACULA это исправится автоматически — стоит отметить как бонус, а не баг.

### 9. `data-*` атрибуты в render.js не обновлены в плане

План (Шаг 3.4) говорит обновить data-атрибуты, но `collectWordData` в reading.js:881 читает `span.getAttribute('data-w')` — после миграции это поле должно браться из `token.surface`, а не `token.w`. Надо синхронизировать render.js и reading.js.

### 10. `morphology-decoder.mjs` — баг с наклонениями

Код `D` для повелительного наклонения (imperative) не раскодируется: `глаг., ..., причастие, D`. Сырой `D` попадёт в UI. Надо починить MACULA-декодер до миграции, а не после.

### 11. `scripts/lib/text-utils.js` — удаление безопасно

Проверено: используется только в `convert-alignments.js`, `verify-alignments.mjs`, `refine-alignments.mjs` — все три в списке на удаление. `greek-translit.mjs` — только в `build-frequency.mjs`. Оба можно удалять.

## Упущения

### 12. Нет миграции пользовательских словарей

`lexemeId` в MACULA имеет формат `grc-paylos-65b926` (детерминированный хеш). Старый формат: `"logos"`, `"theos"` (человекочитаемые id из core.json). Пользовательские словари в localStorage завязаны на старые lexemeId. После обогащения core.json (Шаг 2) нужно либо сохранить старые id, либо написать маппинг старый→новый и мигрировать localStorage.

### 13. Не указана верификация всех 27 книг

План (Шаг 8) говорит «Ручная проверка: все 5 режимов работают» — но не специфицирует, что нужно проверить токенизацию всех 27 книг. Spot-check 1 Кор 1:1 — недостаточно.

### 14. Не обновлён `vite.config.js`

В рисках упомянут runtimeCaching для `data/generated/macula/`. После переноса выхода в `bibles/grc/` нужно обновить и PWA-кеширование.

### 15. `frequency.json` — несовместимость полей

| Поле (старое) | Поле (новое MACULA) |
|---|---|
| `count` | `tokenCount` |
| `strong` (number) | `strong` (array of strings) |
| `rank` | `rank` (совпадает) |
| `translit` | `transliteration` |
| `hasAlignment` | **отсутствует** |
| — | `denseRank`, `coverage`, `coveragePercent`, `cumulativeCoverage`, `isFunctionWord`, `glossesEn`, `firstRef` |

Код `buildWordEntries` (reading.js:599) делает `freqByStrongCache.set(String(item.strong), item)` — с новым форматом `item.strong` это массив, `String(["3972"])` → `"3972"` (работает для одного Strong), но семантически неправильно. И `countActiveWords` (dictionary.js) использует `frequencyList` — нужно проверить совместимость.

### 16. `hasAlignment` отсутствует в новом frequency.json

Старый `frequency.json` содержит поле `hasAlignment` (boolean), которое используется для определения, можно ли выровнять слово с русским переводом. Новый формат этого поля не имеет. Нужно либо добавить его в MACULA pipeline, либо исключить зависимость от него в коде.

## Рекомендации

1. **Разделить план на две независимые ветки:** (A) смена источника grc + адаптер + движок, (B) обогащение лексикона. (B) можно делать сразу и независимо.
2. **До Шага 1:** написать и запустить скрипт сравнения токенизации всех 27 книг (старый grc vs MACULA) — пара строк на Python.
3. **Починить MACULA morphology-decoder** (код `D` → `повел.`, 1-е лицо для местоимений) до миграции.
4. **Strong:** принять явное решение — либо `strong[0]` (с документированной потерей multi-Strong), либо хранить массив и адаптировать все места сравнения.
5. **Добавить mapping `lexemeId`:** старый `core.json` id → MACULA `lexemeId` для миграции пользовательских словарей.
6. **Добавить feature flag** (`useMaculaGrc`) в settings — чтобы можно было откатиться на старый источник без пересборки.
7. **Шаг 4 (выход в `bibles/grc/`):** либо сохранить nested-формат, либо переименовать выход в `bibles/grc-macula/` и не смешивать с legacy.
8. **Обновить план:** явно перечислить все места, где `frequencyList.find(f => f.strong === strong)` ломается от смены формата, и все места, где читаются `data-w`/`data-morph`/`data-strong` атрибуты.
9. **Добавить `hasAlignment`** в MACULA pipeline или убрать зависимость от него в коде приложения.
