## 1. Контекст (почему возник вопрос)

**Контекст (почему возник вопрос).**  
В проекте «Греческая читалка Нового Завета» есть историческая и текущая сложность с идентификацией и выравниванием слов (русское слово Синодального ↔ греческая лемма/форма из SBLGNT). Пользователь/разработчик видит «путаницу»: несколько скриптов в `npm run build:data`, упоминания abandoned Clear-Bible manual alignment, ручные `ruMatches` в core.json, Zefania-теги, Strong-номера, частотный каталог, UBS-домены в `data-sources/`, большая коллекция в `docs/greek-nt-frequency-sources/`. Нужно чётко описать, **какие оригинальные источники реально присутствуют**, как они используются сейчас в пайплайне выравнивания (modes 3–4), и **как лучше всего достичь продуктовых целей** (высокая точность замен, ручное управление пользователем, только проверенные соответствия, offline-first статические данные) с помощью именно этих источников — без введения новых внешних данных или ослабления принципов (см. AGENTS.md, DEVELOPMENT_1 разделы 3–4, DEVELOPMENT_4 «точность важнее покрытия», ALIGNMENT.md).

**Продуктовые цели (из DEVELOPMENT_1 3.4 + 4.4 + DEVELOPMENT_4).**
- Замены слов (режимы 3–4) — **только по выравниванию** (Strong-based). Стих без alignment получает только буквенный слой.
- Только «проверенные» соответствия (из core-лексикона) участвуют в пользовательском словаре и подстановках (hasAlignment gate + ruMatches guard).
- Precision >> recall: лучше не заменить, чем показать неверную лемму/форму (ложные замены хуже нуля для обучения).
- Пользователь полностью вручную управляет набором слов (showInText, статусы, per-word intensity/forms). Никакой авто-адаптации.
- Лемма (режим 3) vs реальная форма (режим 4) — явное различие.
- Частотный каталог (top-1000) — для навигации и будущего расширения, но включаемые слова ограничены проверенными.
- Все данные статические, генерируются скриптами, коммитятся; новые источники — только после license review + решения владельца.

**Оригинальные источники, реально присутствующие и используемые (инвентаризация на 2026-06-15).**

1. **SBLGNT.tsv** (`docs/clear-bible-alignments/SBLGNT.tsv`, Clear-Bible/Alignments commit 6473aa4)  
   - Единственный источник греческих токенов: `{w, lemma, morph, strong}`.  
   - Лицензия: текст SBLGNT — CC-BY 4.0 (SBL + Logos); метаданные — CC-BY 4.0 (Clear Bible).  
   - Использование: `convert-alignments.js` → `assets/data/bibles/grc/*.json`; греческая сторона всех alignment-пар; `build-frequency.mjs` (подсчёт лемм по Strong).  
   - Не чистый SBLGNT (есть отдельные TR-чтения типа Рим 16:24, отсутствуют некоторые другие); задокументировано в `textual-audit.md`.

2. **rus_nt_strongs.xml** (`assets/data/rus_nt_strongs.xml`, Zefania XML, "Russian New Testament Strongs", RusVZh / Victor R. Zhuromsky, 2009, Free Bible Software Group)  
   - Источник Strong-номеров **на русской стороне**: в каждом стихе `<gr str="3056 3588 ...">Слово</gr>` и т.п. (многострочные Strong на одно слово).  
   - Использование (главный драйвер покрытия): `apply-zefania-alignments.mjs` парсит XML → жадно выравнивает слова Zefania с bolls.life-текстом (окно ±15) → переносит Strong'и → генерирует alignment-пары по Strong + sequential consumption на SBLGNT-токены (src:'z').  
   - Покрывает большинство знаменательных слов; даёт реальные, а не regex-выравнивания.

3. **Синодальный текст (bolls.life SYNOD)**  
   - Генерируется `scripts/build-syn.mjs` → `assets/data/bibles/syn/*.json` (base text).  
   - Zefania-слова sequence-align'ятся именно к этому тексту (чтобы перенести Strong).  
   - Public domain.

4. **core.json** (`assets/data/lexicon/core.json`, hand-curated, ~100 записей)  
   - **Ключевой «верифицированный мост»** проекта: `{id, lemma, strong, gloss, pos, ruMatches: [regex...], ruExclude, freqNT, refs...}`.  
   - Роли:
     - Fallback-источник alignment в apply-zefania (когда у слова нет Zefania-Strong).
     - **Runtime guard** в `src/engine/form-layer.js` (даже при Zefania-alignment для core-слов: чистое слово должно матчиться ruMatches + не excluded — иначе замена отклоняется).
     - Определение «Доступные» слов (hasAlignment=true только у Strong, которые реально участвовали в сгенерированных парах; на практике = слова core).
     - Глоссы, POS, идентификатор lexemeId для карточек и personal dictionary.
   - Редактируется вручную (синхронно с ростом покрытия и проверкой на реальном Синодальном). Не генерится автоматически.

5. **Вспомогательные / справочные источники в репо (`data-sources/`).**  
   - `strongs-dictionary.json`, `strongs-greek.json`, `strongs-ru-alignment.json` (эмпирические топ-слова по Strong на русском).  
   - `ubs-greek-dictionary.json`, `ubs-lexical-domains.json`.  
   - Использование: скрипты `add-ubs-senses.py`, `add-detail.py`, `translate-top100.py` и т.п. — для обогащения глоссов/доменов в core.json (улучшение качества карточек), анализа покрытия, построения strongs-ru-alignment.  
   - **Не используются** для генерации alignment-пар и расширения множества заменяемых слов (это было бы нарушением «проверенные соответствия»).

6. **Коллекция `docs/greek-nt-frequency-sources/` (macula-greek, opengnt, morphgnt-sblgnt, sblgnt raw, stepbible-data, core-gnt-vocab и др.).**  
   - Альтернативные разметки, частотники, морфология, низкоуровневые деревья.  
   - Текущий статус: **не используются** в основном пайплайне (build-frequency намеренно считает частоты только по собственным `grc/*.json`).  
   - Причина: license review (см. `notes/license-review.md`, `notes/next-steps-for-frequency-builder.md`). Расширение частотного слоя глоссами отсюда — отдельное решение владельца после аудита.

7. **Собственные производные (всегда регенерируются скриптами, править руками — запрещено).**  
   - `assets/data/bibles/syn/*.json` (текст + alignment[] с полями ru/gr/src/q/c после refine).  
   - `assets/data/bibles/grc/*.json`.  
   - `assets/data/lexicon/frequency.json` (top-1000 лемм + rank + count + translit + hasAlignment; чисто из корпуса проекта).  
   - `assets/data/textual-variants.json` (авто-реестр TR-плюсов / версификационных расхождений).  
   - `test/fixtures/gold-dev.json` + `gold-heldout.json`, refine/verify-логи.

**Текущий пайплайн выравнивания (точно соответствует `package.json` "build:data").**
```
build:data =
  apply-zefania-alignments.mjs   # 1. Zefania Strong (primary) + lexicon fallback → alignment в syn
  && convert-alignments.js       # 2. Генерация grc/*.json из SBLGNT.tsv; возможно, legacy/дополнение
  && refine-alignments.mjs       # 3. Pass A (αὐτός-прономены), B (downgrade в q:u по спискам служебных/классов), C (q-cascade + dedup)
  && build-frequency.mjs
```
- В `form-layer.js` и `compose.js` (режимы 3–4): пары с `q === 'u'` отбрасываются; для core-слов — дополнительный ruMatches-guard.
- Sequential consumption Strong (Map + usage count) — для повторов одной леммы (Ин 1:1 «Слово» → три разных λόγος).
- Метрики после refine (из DEVELOPMENT_6/7 + verify): ~108k пар, ~93.5% видимых (e+f), precision 99–100% на gold-heldout, recall ~95%.

Это **реализация методологии ALIGNMENT.md** (трёхуровневая шкала качества, пост-обработка вместо переписывания генератора, морфология из источника, реестр вариантов, gold + held-out, объяснение всех сирот).

**Почему «путаница» возникла (диагноз).**
- Документация и комментарии в скриптах частично отражают предыдущие итерации (regex-only word-layer, попытка Clear-Bible SBLGNT-RUSSYN-manual.json — была удалена из-за рассогласования токенизации target-ID; см. clear-bible-alignments/README.md и textual-audit.md).
- В цепочке build:data участвуют apply + convert + refine — зрительно «много источников».
- Двойная природа «проверенного слова»: (а) Zefania даёт Strong на много слов; (б) только ~98 из них имеют запись в core.json и поэтому становятся «Доступные» + guarded. hasAlignment в frequency — честный маркер этого ограничения.
- Дополнительные `data-sources/` и огромная папка greek-nt-frequency-sources лежат в репо, но их роль (справочные для обогащения core, а не для alignment) не всегда очевидна из живых доков.
- Ключи слов: `lexemeId` из core (человеко-читаемый) vs `freq-<strong>` (для каталога) vs plain Strong (мост между RU и GR).
- В старых roadmap'ах (DEVELOPMENT_1..3) описан regex-механизм, который DEVELOPMENT_4 сознательно заменил на alignment-only.

**Рекомендуемый подход (как лучше всего достичь целей, используя именно эти источники).**

**Принцип:** не добавлять новые источники и не ослаблять гейт; максимально использовать сильные стороны уже имеющихся трёх «канонических» (Zefania + SBLGNT.tsv + core ruMatches) + refine как лингвистический слой.

1. **Зefania XML — основной источник покрытия и точности выравнивания (уже так и есть).**  
   Даёт реальные, авторские Strong-соответствия на русской стороне. Последовательное потребление + sequence-align к bolls.text решает проблему «один Strong — много вхождений». Это лучше, чем чистый regex или ручные пары (которые и были проблемными).

2. **core.json ruMatches — firewall точности и «учебный словарь».**  
   - Никогда не удалять guard в form-layer (решение DEVELOPMENT_4 №3).  
   - Расширение покрытия = добавление новых вручную выверенных записей в core (ruMatches по реальному Синодальному + gloss + refs). Это растит и hasAlignment, и «Доступные».  
   - ruMatches остаются также fallback'ом в apply-zefania.

3. **SBLGNT.tsv — единственная истина для греческой стороны.** Не менять, не подмешивать другие Greek NT (macula и пр.) без отдельного решения.

4. **refine-alignments + verify + gold fixtures — обязательный лингвистический и измерительный слой.**  
   Продолжать расширять ручную разметку gold (DEVELOPMENT_7) для измерения *истинности*, а не только стабильности. Инварианты + whitelist + held-out метрики — часть гейта `npm run verify:data`.

5. **data-sources/ (UBS + Strongs) — только для качества карточек, не для расширения alignment.**  
   Использовать в `add-ubs-senses.py` и аналогах для улучшения gloss/доменов существующих core-записей. Автоматически добавлять новые леммы из них в core/alignment — **запрещено** без license review + решения владельца.

6. **greek-nt-frequency-sources/ — держать за пределами основного пайплайна** (как сейчас). build-frequency остаётся на собственном корпусе. После license review можно рассмотреть обогащение frequency.json глоссами (не alignment'ами).

7. **Частотный слой и экран словаря.**  
   Показывать весь top-1000 как каталог (ценность сама по себе). Фильтр «Доступные» + честные подписи («Нет проверенного русско-греческого соответствия — слово пока не участвует в подстановках») — правильное отражение текущего состояния (98 включаемых). freq-* записи в personal dictionary — fail-soft (код есть, но hasAlignment=false у non-core, и создать их через UI нельзя).

8. **Документация и коммуникация (самое важное для устранения «путаницы»).**  
   - Обновить живые разделы DEVELOPMENT_1.md (3.5 таблица источников, 3.3 модель alignment, 3.4 движок) и README/«О приложении», чтобы явно назвать триаду: Zefania (RU Strong) + SBLGNT.tsv (GR tokens) + core ruMatches (verified bridge + guard).  
   - Добавить/расширить короткий документ (например `docs/development/WORD_ALIGNMENT_SOURCES.md` или раздел в ALIGNMENT.md), с диаграммой потока и ролями каждого источника.  
   - В скриптах (особенно apply-zefania и convert) оставить/дополнить комментарии «почему именно так».  
   - В word-card / dictionary при необходимости (опционально) показывать provenance одной строкой («выровнено по Strong Zefania» или просто полагаться на guard).  
   - DEVELOPMENT_2/3/4/5/6/7 и старые отчёты — оставить как архив (они уже содержат честную историю).

9. **Операционные правила (AGENTS.md).**  
   - Любое изменение источников/пайплайна → `npm run build:data` + `npm run verify:data` + инварианты + spot-check ключевых стихов (Ин 1:1, Мк 1:1 и т.д.).  
   - Перед «готово» — `npm test && npm run build`.  
   - Новые слова в core — только с ruMatches, выверенными по реальному тексту Синодального.  
   - Никогда не править руками сгенерированные alignment в syn/*.json.

**Ожидаемый эффект.**  
- Устранение путаницы: один ясный источник правды о словах (триада + refine как пост-обработка).  
- Сохранение (и усиление) уже достигнутого качества (precision 99–100%, честное объяснение непокрытых ~6.5% + сирот).  
- Чистый путь расширения в будущем: расти core.json (или после license — осторожно импортировать из внешних, применяя тот же refine/guard/q-дисциплин).  
- Соответствие всем жёстким ограничениям проекта (детерминизм, чистые данные, ручное управление обучением, точность важнее покрытия).

**Критическая оценка текущего состояния и предлагаемого направления (на основе исследования кода, данных и документов, 2026-06-15)**

**Неочевидные слабости текущего пайплайна (причина «путаницы»):**

- Многостадийность + распределённая истина. apply-zefania (Zefania primary) → convert → refine → frequency. В большинстве сгенерированных alignment в syn/*.json сейчас только `{ru, gr}` (Ин 1:1 — 13 пар). Поля `src`/`q`/`c` присутствуют выборочно. Даже после всего refine «почему именно эта пара» — результат композиции четырёх источников + правил.

- Zefania уже сильно расширила покрытие: в текущих данных frequency.json имеет hasAlignment: true у всех 1000 записей, core.json = 204 записи, и не все hasAlignment-леммы лежат в core. Guard ruMatches остался только для слов с regexps в core. Ограничение «только core выравниваются», которое сознательно защищали в DEVELOPMENT_4/5, де-факто ослабло. Это хорошо для покрытия, но усиливает путаницу «что считается проверенным словом».

- Исторический долг в доках, комментариях и скриптах (упоминания abandoned Clear-Bible manual alignment, старые описания regex word-layer). Любой новый агент тратит время на ту же археологию.

- Регенерация — дорогая операция. Обновление базового текста или SBLGNT snapshot требует перепрогона refine, актуализации gold, spot-check'ов и возможной правки text-utils.js. Это и есть практическая боль.

**Неочевидные риски и слабости «сделать один большой LLM+человек-курируемый Word Bank на ~1000 слов + выравнивания, заморозить, почти не запускать скрипты, верифицировать в несколько LLM-проходов»:**

- Лицензии и атрибуция. Большой банк выравниваний — новая производная работа. Нужно атрибутировать SBLGNT (CC-BY 4.0), Clear Bible metadata, Zefania XML (нужна точная лицензия), UBS и т.д. не только в «О приложении», но и в самом банке для спорных решений. «Один раз LLM и закоммитили» не снимает обязанностей.

- Потеря воспроизводимости. Через 1–2 года «почему именно это вхождение выровнено так» будет иметь ответ только в истории чатов и памяти разработчика, а не в коммитнутых исходниках + детерминированном скрипте.

- Греческие surface-формы и морфология всё равно нужны per-verse (режимы 4 и 5). Bank на уровне лемм не отменяет grc-токены.

- Дрейф русского текста. bolls.life snapshot в syn/*.json — фиксирован. Известный долг 2 Кор 11:32/33. При любом обновлении базового русского текста нужно будет переприменять выравнивания к новой токенизации.

- Масштаб верификации. Полноценная проверка качества тысяч пар — это примерно та же работа, которую уже проделали через refine + gold + verify. Скорее всего «несколько проходов» заново откроют необходимость тех же лингвистических проходов (αὐτός, function words, TR-плюсы и т.д.).

- Продуктовый объём. Переход от ~200 curated слов (из которых ~100 «Доступные» для обучения) к активной работе с 1000 словами меняет весь педагогический контракт, онбординг, словарь, прогресс. Это не техническая замена, а новая большая фича.

- Риск для существующих пользователей. Изменение ключей (lexemeId / strong) в банке сломает IndexedDB-словари пользователей.

- «Никаких скриптов» — иллюзия. Даже с идеальным банком почти наверняка понадобится хотя бы минимальный emitter, чтобы из банка + base-текстов получить ровно те лёгкие формы, которые ждут текущие engine, reading.js и тесты. Полная заморозка без генератора = широкая переделка контрактов.

- SQLite в клиенте — новая зависимость (против духа AGENTS.md).

**Сбалансированная рекомендация (гибрид, который уважает желание пользователя и все правила проекта)**

Сделать **Word Bank** (курируемый JSON / набор JSON) **единственным медленно меняющимся источником правды** о словах, глоссах, выравниваниях и качестве (с полями provenance, quality, notes, refs на уровне конкретных решений). 

LLM + несколько слепых верификационных проходов + живое обсуждение с разработчиком — именно так, как предлагает пользователь.

Параллельно ввести **минимальный детерминированный emitter** (один-два скрипта), который берёт Word Bank + закоммиченные base-тексты (текущие syn/grc) и выдаёт ровно те же лёгкие артефакты, которые сейчас потребляет приложение. Все тесты, движок, UI продолжают работать без изменений.

После большого успешного кураторского прохода тяжёлый пайплайн (apply + convert + refine) переводится в статус «legacy, только для редкого refresh upstream». Обычная работа — правка Word Bank + emitter + обычные гейты.

Это даёт:
- Почти то, что хочет пользователь («один раз качественно составили — дальше почти не пересобираем»).
- Сохранение «не правим руками сгенерированные данные».
- Сохранение лицензионной и аудиторской гигиены (исходники SBLGNT.tsv и Zefania остаются; банк явно документирует происхождение каждого решения).
- Возможность в будущем обновить базы без потери всего.

**План работ (рекомендуемый порядок)**

1. **Инвентаризация и критическая оценка** (этот документ) — уже сделано.
2. **Проектирование формата Word Bank** (поля на лемму + явные выравнивания/решения по сложным вхождениям, provenance, качество e/f/u + заметки).
3. **Пилот** (30–60 слов, включая все известные сложные случаи αὐτός, Ин 1:1, несколько TR-плюсов, служебные слова, генеалогии). LLM готовит предложения с цитатами из источников; 2–3 слепых прохода верификации + живое обсуждение расхождений.
4. **Протокол и инструменты верификации** (слепые промпты, gold + случайная выборка, сравнение с текущим alignment, инварианты).
5. **Полный проход + emitter** + перегенерация данных + обновление тестов/документации (DEVELOPMENT_1, ALIGNMENT.md, скрипты, README).
6. **Миграция pipeline** в package.json и docs: emitter становится основным; старые скрипты — опционально/legacy.
7. **Полная верификация** (те же гейты + ручная проверка на ключевых стихах + regression сравнение старого/нового alignment на gold).

**Критические файлы (для справки при исполнении)**
- Новые: `assets/data/lexicon/wordbank.json` (или директория), `scripts/build-from-wordbank.mjs` (emitter).
- Изменяемые: `package.json` (build:data), `docs/development/DEVELOPMENT_1.md`, `docs/development/ALIGNMENT.md`, `scripts/apply-zefania-alignments.mjs` и др. (добавить пометку legacy), тесты данных.
- Не трогать без необходимости: контракт Segment, форму alignment в runtime (emitter должен выдавать совместимый формат), схему IndexedDB.

**Верификация (обязательна после любых изменений по этой теме)**
- `npm run build:data && npm run verify:data` (0 ошибок).
- `npm test` (особенно тесты, грузящие реальные данные).
- `npm run build`.
- Ручная проверка: Ин 1:1, Мк 1:1, случаи с αὐτός, невыровненные TR-стихи, переключение режимов 3/4, словарь (Доступные + Все), мобильный + десктоп, светлая/тёмная.
- Сравнение метрик precision/recall на gold-dev/heldout до и после (не хуже).
- Git: чисто; данные регенерированы emitter'ом, а не правлены руками.

Этот подход максимально приближает пользователя к желаемому «один раз качественно составили и пользуемся», при этом не нарушает ни одно жёсткое правило проекта и сохраняет возможность аудита и обновления баз.
