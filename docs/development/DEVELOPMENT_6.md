## Шаг 4 — `scripts/refine-alignments.mjs`

**Самый сложный скрипт.** Постобработчик, который читает syn JSON после `build:data`,
применяет лингвистические правила и пишет обратно.

### Проход A: исправление G846 (αὐτός) → личное местоимение

**Вход:** стихи, где `αὐτός` выровнен на «свой», а рядом есть невыровненное
«его/него/ему…»

**Два фильтра:**
1. **Предложный (первичный):** если G846 идёт после греческого предлога — ключ =
   `(предлог, падеж G846 из поля c)`. Найти orphan за русским предлогом из `PREP_TABLE`.
   Падеж сироты должен быть совместим с таблицей.
2. **Падежный (fallback):** для беспредложных G846. Таблица `CASE_COMPAT`.
   Пересечение cases **И** numbers. Род — мягко (предпочтение, не запрет).

**Алгоритм:**
1. Собрать orphans: `[{idx, word, cases, numbers, genders}]` — из `RU_PRONOUNS`
2. Найти пары `gr.strong === 846` И `ru` ∈ `SVOV_FORMS`
3. Для каждой: фильтр 1 или 2
4. Найти orphan с непустым пересечением cases ∩ numbers. Род при нескольких
   кандидатах — tiebreaker.
5. Нет совместимых → оставить `q:"f"`. **Без позиционного fallback.**
6. Nom-сироты → только от Nom-αὐτός.
7. После перенаправлений: если ровно один невыровненный G846 и ровно один
   orphan → добавить пару `src:"a"`.

**Порядок обработки:** по возрастанию gr-индекса (детерминизм).

### Проход B: понижение качества (до `q:"u"`)

1. `gr.strong === 3588` И НЕ (`ru` ∈ `SUBST_ARTICLE_RU` И соседний токен ∈ `SUBST_ARTICLE_GR`)
2. `ru` ∈ `SVOV_FORMS` И `gr.strong` ∉ `SVOV_LEMMAS`
3. `gr.strong === 3303` (μέν) И `ru` ≠ "итак"
4. Классовое несоответствие (русское служебное ↔ греческое знаменательное) на любой дистанции
5. Прыжок > 12 без классового несоответствия — **не трогать** (warn в верификаторе)

**Белый список (не понижать):**
- G2400 (ἰδού) ↔ вот/се → `q:"e"`
- G302 (ἄν) ↔ бы → `q:"f"`
- `gr.strong` ∈ `SVOV_REFLEXIVE` ({1438, 2398, 4572, 1683}) ↔ свой/… → `q:"e"`
- G846 ↔ свой/… (оставшиеся после прохода A) → `q:"f"`
- G3588 + G1161/G3303 ↔ `SUBST_ARTICLE_RU` → `q:"f"`
- G3303+G3767 (μὲν οὖν) ↔ итак → `q:"f"`

### Проход C: q-каскад и валидация

**Удалить:** индексы вне границ; проигравший дедупликации (`z` > `a` > `l` > удалить).

**q-каскад (по приоритету):**
1. Спецусловия (белый список, правила B) → как указано
2. `src === "z"` → `q:"e"`
3. `src === "a"` → `q:"e"`
4. `src === "l"` → `q:"u"`

**Требования:** идемпотентность (`refine(refine(x)) === refine(x)`), dry-run режим
(`--dry-run` пишет лог, не трогает файлы), все правила ключевать по Strong's
numbers, нормализация через `cleanRuWord()`.

## Шаг 6 — LLM-верификация

- 600 случайных пар из множества `e+f`
- **Слепой формат:** LLM получает текст + токены без готовых пар, выравнивает с нуля
- Основной промпт (500 пар): с эвристиками refine
- Контрольный промпт (100 пар): без номеров Стронга, без эвристик — «выровняй прямые
  лексические эквиваленты». Порог: ≥ 3 расхождений одного паттерна → правило на пересмотр
- Diff → адъюдикация → подтверждённые ошибки
- Расхождение экземпляров одинаковой леммы → "minor", не ошибка
- Критерий: ≤ 1 подтверждённая ошибка на 600
