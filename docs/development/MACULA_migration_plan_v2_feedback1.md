# Feedback: MACULA Migration Plan v2 — Critical Review

**Date:** 2026-06-17
**Author:** Claude (systematic review)

---

## Общая оценка

v2 — серьёзный шаг вперёд по сравнению с v1. Правильные архитектурные интуиции:
разделение source/canonical/runtime/user слоёв, `lexemeKey` вместо MACULA-хешей,
явная не-цель «100% coverage alignment», fail-closed на uncertain matches,
сохранение `core.json` как курируемого слоя.

**Но v2 создаёт новые проблемы, которых не было в v1, и некоторые из них —
блокирующие для практической реализации.**

---

## 1. Блокирующие проблемы

### 1.1 Переусложнение data layers для соло-проекта

v2 предлагает 4 слоя данных:
- Source layer (`docs/sources/`)
- Canonical generated layer (`generated/canonical/`)
- Runtime offline layer (`assets/data/`)
- User state layer (IndexedDB)

Плюс структура путей с тремя независимыми файлами на каждую книгу:
```
assets/data/translations/syn/books/john.json
assets/data/originals/sblgnt-macula/books/john.json
assets/data/align/syn--sblgnt-macula/books/john.json
```

**Проблема:** для соло-разработчика это экспоненциальный рост сложности.
Текущая архитектура (2 файла на книгу: `bibles/syn/john.json` + `bibles/grc/john.json`)
работает. Три файла вместо двух — это +50% запросов, +50% точек отказа,
+50% кода загрузчика.

**Контр-предложение:** объединить translation и alignment в один файл (как сейчас —
alignment внутри syn-книги), а original оставить отдельно. Два файла на книгу,
а не три.

### 1.2 Полная перестройка выравнивания — это отдельный проект

v2 предлагает построить `syn--sblgnt-macula` alignment с нуля, с gold-heldout,
sampled blind review, textual variant registry, regression comparison.

**Проблема:** это не часть миграции данных. Это отдельный исследовательский проект
на несколько недель. Текущее выравнивание в `syn/*.json`:
- построено детерминированно по Strong + ruMatches;
- проверено инвариантами;
- работает в проде для 98 слов core-лексикона;
- имеет известные ограничения (54% non-core слов без alignment).

Заменить его «правильным» выравниванием — благородная цель, но она блокирует
всю миграцию. Нельзя переходить на MACULA, пока не готово новое выравнивание.
А новое выравнивание нельзя сделать быстро.

**Контр-предложение:** разделить миграцию на два независимых трека:
- **Трек A (data migration):** заменить источник греческих данных на MACULA,
  сохранив существующее выравнивание. Это можно сделать за дни.
- **Трек B (alignment rebuild):** построить новое выравнивание как отдельный
  проект, не блокирующий трек A.

### 1.3 Поле `words` в translation book — скрытая сложность

v2 предлагает хранить токенизированные слова в translation book:
```json
"words": ["В", "начале", "было", "Слово"]
```

**Проблема:** русская токенизация — сложная задача. Составные предлоги
(«в течение»), частицы («-ка», «-то»), дефисы («из-за»), церковнославянизмы
в Синодальном тексте — всё это создаёт крайние случаи.

Текущий подход (`ruMatches`-регулярки в `core.json`) не требует полной
токенизации текста — он ищет совпадения по регуляркам в тексте стиха.
Переход на токенизацию «всего текста» означает, что любая ошибка токенизации
ломает выравнивание для всего стиха, а не только для одного слова.

**Риск:** детерминированный токенизатор, написанный для миграции, будет иметь
свои баги. Каждый баг токенизации → расхождение с выравниванием → «невидимое»
слово в режимах 3-4.

**Контр-предложение:** отложить полную токенизацию до трека B. Сначала
мигрировать греческие данные, сохранив regex-based matching для выравнивания.

## 2. Архитектурные проблемы

### 2.1 `generated/canonical/` и `assets/data/` — дублирование данных

v2 предлагает два выходных каталога:
- `generated/canonical/` — полные данные для аудита
- `assets/data/` — компактные данные для PWA

**Проблема:** это означает, что pipeline должен генерировать одни и те же данные
дважды — в полном и компактном формате. Это удваивает код генерации, удваивает
время сборки и создаёт риск расхождения форматов.

**Контр-предложение:** генерировать ТОЛЬКО в `assets/data/` (компактный формат),
а для аудита использовать тот же файл + отдельный audit report (JSON небольшого
размера с aggregate statistics). Не дублировать данные.

### 2.2 `data-manifest.json` с `precache: true` для top-1000

v2 предлагает precache top-1000 lexicon (цель: под 1 MB).

**Проблема:** текущий PWA precache — 15 файлов, 1.6 MB. Добавление top-1000
lexicon в precache увеличит начальную загрузку на ~1 MB. Для пользователя на
медленном мобильном интернете это заметно.

**Вопрос:** что важнее — чтобы словарь работал совсем без интернета, или чтобы
первая загрузка была быстрой? Ответ зависит от сценария использования, и это
продуктовое решение, а не архитектурное.

**Контр-предложение:** использовать runtime caching (StaleWhileRevalidate)
для top-1000, а не precache. Словарь загрузится при первом открытии и потом
будет доступен офлайн. Это не требует изменения текущей PWA-стратегии.

### 2.3 `lexemeKey` vs `id` vs `maculaLexemeId` — три идентификатора

**Проблема:** v2 вводит три системы идентификации леммы:
- `lexemeKey` — app-level ключ (logos, theos, …)
- `id` / `maculaLexemeId` — MACULA-хеш
- `strongs` — массив номеров Стронга

Это три разных способа сослаться на одну и ту же лемму. Каждый consumers
(движок, UI, словарь, выравнивание, indexedDB) должен знать, какой ID использовать.
Неизбежны баги, когда используется «не тот» ID.

**Контр-предложение:** использовать `lexemeKey` как PRIMARY key везде в коде
приложения. `maculaLexemeId` — ТОЛЬКО для обратной связи с MACULA (в данных,
не в коде). `strongs` — ТОЛЬКО для выравнивания. Правило: если ты в
`src/engine/` или `src/ui/`, ты используешь `lexemeKey`.

### 2.4 Три файла на книгу = утроение точек отказа для офлайна

Для чтения Ин 1 в режиме 3 нужны ВСЕ три файла:
```
translations/syn/books/john.json    — русский текст
originals/sblgnt-macula/books/john.json — греческие токены
align/syn--sblgnt-macula/books/john.json — выравнивание
```

**Проблема:** если alignment-файл не закеширован, греческий слой падает целиком
(режимы 3-5), даже если original-файл уже загружен. В текущей архитектуре
alignment внутри syn-файла — одна точка отказа вместо двух.

## 3. Проблемы реализуемости

### 3.1 9 фаз — это не план, это дорожная карта на месяцы

v1: 8 шагов, ~8-12 часов.
v2: 9 фаз, каждая с подпунктами. Реалистичная оценка: 4-8 недель.

**Проблема:** соло-разработчик не может удержать в голове 9 фаз изменений.
План должен помещаться в одну итерацию (1-2 недели), иначе он устареет
раньше, чем будет выполнен.

### 3.2 Phase 4 (Verification gates) — академический overkill

Gold-heldout, sampled blind review, textual variant registry, regression
comparison, precision/recall thresholds...

**Проблема:** это методология научной публикации, а не приложения-читалки.
Для продукта достаточно:
1. Инварианты (schema, bounds, duplicates)
2. Spot-checks (Ин 1:1, Мф 1:1, несколько случайных стихов)
3. Consistency check (частоты не изменились, покрытие не упало)

Всё остальное — отличная цель для отдельного проекта по качеству выравнивания,
но не для миграции данных.

### 3.3 Отсутствие adapter'а = big-bang переключение

v2 отвергает adapter (v1 Step 1) как «сохраняющий старую архитектуру».
Вместо этого предлагает переписать ВСЁ: загрузчики, движок, форматы, кеширование.

**Проблема:** без adapter'а нет постепенного перехода. Новый код либо работает
целиком, либо приложение не запускается. Это максимальный риск.

**Контр-предложение:** adapter на уровне данных (а не кода): `build-macula.mjs`
генерирует runtime-файлы в формате, который может читать СТАРЫЙ загрузчик.
Потом загрузчик обновляется. Старый формат удаляется. Три шага, а не один big-bang.

### 3.4 BSB-совместимость с первого дня

v2 встраивает поддержку Berean Standard Bible в фундамент архитектуры:
`translations.json`, `originals.json`, `alignmentId`, paths for `bsb`.

**Проблема:** BSB — это будущее. Его нет в проекте. Проектирование под будущее,
которого может не случиться (или которое будет иметь другие требования) —
классическая ловушка overengineering.

**Контр-предложение:** использовать конвенцию имён, которая НЕ мешает добавить
BSB потом (например, `bibles/syn/` и `bibles/grc/` — уже расширяемо), но НЕ
создавать абстракции `translations.json`/`originals.json` до реальной необходимости.

## 4. Проблемы, унаследованные от v1 и не решённые

### 4.1 Что делать с выравниванием?

v1: сохранить существующее выравнивание (через adapter).
v2: построить выравнивание заново (дорого, долго).

**Ни один план не предлагает:** проверить, работает ли СУЩЕСТВУЮЩЕЕ выравнивание
с MACULA-токенами. Алгоритм выравнивания в `convert-alignments.js`:
1. Ищет русское слово по `ruMatches`-регулярке
2. Находит греческий токен с тем же номером Стронга
3. Сопоставляет их

MACULA-токены содержат те же номера Стронга. Те же регулярки. Те же книги.
**Выравнивание можно просто перегенерировать с MACULA-токенами вместо Clear-Bible.**
Это не требует нового алгоритма, gold-heldout или blind review.

### 4.2 Ни один план не объясняет частотный сдвиг

При замене источника данных неизбежно изменятся:
- Количество токенов (SBLGNT.tsv: 137 741 vs MACULA: 137 740 — разница в 1 токен!)
- Частоты лемм (могут быть микро-расхождения из-за different tokenization)
- Порядок лемм с одинаковой частотой (сортировка по NFC может отличаться)

**Проблема:** `freq-123` ключи в пользовательских словарях привязаны к рангу.
Если ранг леммы изменился, ключ указывает на другую лемму.

**Этого нет в v1, нет в v2.** Нужна явная проверка: какие `freq-*` ключи
изменятся при переходе на MACULA?

## 5. Сильные стороны v2 (что сохранить)

1. **`lexemeKey` как стабильный ключ.** Правильно. Должен пережить любой data migration.

2. **MACULA = source of truth для греческого, не для русского.** Чёткое разделение.

3. **Fail-closed на uncertain alignment.** `q=u` скрыто от пользователя.

4. **Отказ от 100% coverage как цели.** Accuracy > coverage.

5. **Source manifests с SHA и лицензиями.** Критически важно для лицензионной чистоты.

6. **Cleanup — последним шагом.** Не удалять старые данные до верификации новых.

7. **Детерминизм генерации.** Повторный запуск = идентичный результат.

8. **`isFunctionWord` через конфигурацию, не через эвристику в коде.**

---

## 6. Рекомендуемый путь: v2-minimal

Взять сильные стороны v2, но радикально упростить реализацию:

### Фаза A: Перегенерация grc-данных (1-2 дня)

1. `build-macula.mjs` → дополнительный output mode, который пишет
   MACULA-токены в СТАРОМ формате `bibles/grc/*.json`:
   ```json
   { "w": "λόγος", "lemma": "λόγος", "morph": "N-NSM", "strong": 3056,
     "lexemeKey": "logos", "maculaLexemeId": "grc-logos-04b1f3",
     "isFunctionWord": false, "glossEn": "word" }
   ```
   Старые поля (`w`, `morph`, `strong` как число) — для совместимости.
   Новые поля (`lexemeKey`, `maculaLexemeId`, …) — опционально, для будущего.

2. Перегенерировать `frequency.json` из MACULA (формат — расширенный старый)

3. Запустить старый `convert-alignments.js` на новых grc-данных → alignment обновится

4. Проверить: `npm test`

Результат: приложение работает на MACULA-данных без изменения кода.

### Фаза B: Обновление движка (1-2 дня)

5. `form-layer.js`: поддержка ОБОИХ форматов (старый `w` + новый `surface`)
6. `reading.js`: `buildWordEntries` по `lexemeKey`
7. Обновить тесты

### Фаза C: Cleanup (1 день)

8. Удалить старые скрипты и `clear-bible-alignments/`
9. Обновить документацию
10. `npm test` + `npm run build` + ручная проверка

### Фаза D (отдельный проект): Выравнивание v2

11. Gold-heldout, blind review, улучшение alignment quality
12. Не блокирует фазы A-C.

**Итого: 4-5 дней до работающего приложения на MACULA (против 4-8 недель в v2).**

## 8. Конкретные предложения по изменению v2

1. Разделить на два трека: **data migration** (быстро) и **alignment rebuild** (отдельно).

2. Убрать `generated/canonical/` — генерировать сразу в `assets/data/`
   в компактном формате. Для аудита — audit report (JSON < 100 KB).

3. Объединить translation + alignment в один файл (как сейчас).

4. Отказаться от `translations.json` / `originals.json` до появления BSB.

5. Использовать runtime caching для top-1000, не precache.

6. Упростить verification gates до: инварианты + spot-checks + consistency.

7. Добавить в план явную проверку `freq-*` ключей при миграции частот.

8. Добавить adapter (data-level, не code-level) для постепенного перехода.

9. Сократить фазы до 3 (data, engine, cleanup) + 1 опциональная (alignment v2).
