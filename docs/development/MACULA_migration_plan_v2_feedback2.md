**Date:** 2026-06-17
**Author:** Claude (review 2)

**Исходная посылка заказчика:** «Миграции не нужны — пользователей ещё нет.

---

## 1. Итоговая оценка

Скелет целевой архитектуры здоровый: разделение слоёв
source/canonical/runtime/user, `lexemeKey` вместо MACULA-хешей, `localeId` ≠
`translationId`, source-манифесты, fail-closed на неуверенном выравнивании,
cleanup последним. Это сохранить.

**Но документ построен на неверной посылке.** Это план *безопасной миграции с
откатом и сохранением пользовательского состояния*. У тебя greenfield:
пользователей нет, переносить нечего, откатываться не для кого. Из-за этого

1. ~40 % плана — мёртвый груз (машинерия миграции), его надо **удалить**, а не
   дорабатывать;
2. план **уклоняется ровно от тех решений, которые в greenfield обязаны быть
   приняты один раз и правильно** — то есть от «продуманной модели», которую ты
   и просишь.

Парадокс: разбор v2_feedback1 толкал в сторону «минимально, сохранить legacy,
adapter». Твоя посылка толкает **в противоположную сторону**: раз сохранять
нечего — не нужен ни adapter, ни legacy-baseline, ни dual-run; нужна **одна
правильная модель и одноразовая генерация из MACULA**. Поэтому часть критики
feedback1 («academic overkill») приходится пересмотреть (см. §4.2).

## 2. Главная переориентация: это не миграция

Удалить из плана как нерелевантное при отсутствии пользователей:

| Раздел плана | Что это | Почему мёртвый груз |
|---|---|---|
| §4.2 «old alignment is a legacy baseline / oracle» | сверка с прошлым выравниванием | нет «прошлого», к которому привязаны пользователи; старое выравнивание — просто один из черновиков, не точка отсчёта |
| §4.6 «final runtime has no legacy debt», compatibility bridges | мосты старый↔новый формат | нет старого рантайма у пользователей → нет моста |
| Phase 0 «baseline recording для отката» | запись legacy-состояния | откат не нужен |
| **Phase 5 «User dictionary migration»** | `freq-*`→`lexemeKey`, IndexedDB schema migration, маппинг старых ключей | переносить нечего; просто выбрать схему `lexemeKey` сразу правильно (§3.1) |
| §13 Rollback strategy | data-path откат, fail-soft на старое | нет состояния, в которое откатываться |
| §2.1 «Preserve existing user progress» | сохранение прогресса | прогресса нет |
| Phase 9 в части «do not delete legacy until gates pass», «remove compatibility loaders» | поэтапное удаление legacy | удаляй сразу: это просто файлы в репозитории, не контракт |

**Важно различать два смысла «ничего нет»:**

- **Пользователей нет** → верно → user-миграцию, откат, мосты выкинуть.
- **Курируемых данных нет** → *ложно*. В репозитории лежит ручная работа,
  которую MACULA не заменяет: `assets/data/lexicon/core.json` — **204**
  курируемые леммы (`ruMatches`, `ruExclude`, русские глоссы, `refs`). Это и
  есть актив, который надо беречь. План это место смазывает, говоря только про
  «user progress».

## 3. Чего план не решает (а в greenfield обязан)

Это и есть «продуманная модель». Сейчас на этих местах — отсрочки и хеджи.

### 3.1 Схема `lexemeKey` для некурируемых слов не определена

§4.5 / §6.6: «new frequency-only words can use a deterministic app key, but the
format must be documented and **migrated explicitly**». Мигрировать некого —
надо просто **решить схему ключа один раз**. Это центр всей модели (ключ
пользовательского словаря, выравнивания, UI), и он пуст.

Проверенный факт в пользу простого решения: MACULA даёт **чистое 1:1**
лемма↔лексема — 5468 лемм, у каждой уникальный `lexemeId`, **ноль** коллизий
лемма→несколько `lexemeId` (`assets/data/generated/macula/lexemes.json`).

Рекомендация по схеме:
- 204 курируемых ключа — человекочитаемые (`logos`, `theos`, `kurios`),
  сохраняются дословно;
- остальные — детерминированный ключ из транслитерации + дизамбигуатор
  (`maculaLexemeId` уже содержит хвост-хеш: `grc-logos-04b1f3`). Не брать «голую»
  транслитерацию как ключ — возможны омографы (разные леммы, одинаковый
  `translit`); хвост `maculaLexemeId` снимает коллизию.
- Правило: `lexemeKey` — единственный ключ в `src/engine/**`, `src/ui/**` и
  IndexedDB; `maculaLexemeId` — только в данных (provenance); `strongs` — только
  в выравнивании. (Это уже было в feedback1 §2.3 — поддержать.)

### 3.2 Якорь выравнивания: `tokenId`, а не индекс

§7.7 хранит пары как `{ "r": 3, "g": 4, "tokenId": …, "lexemeKey": … }`. Я
проверил текущие данные — они ровно такие индексные:
`assets/data/bibles/syn/john.json` → `{"ru":3,"gr":4,"src":"z"}`. Это **та же
индексная хрупкость**, что дала исходный баг пары стихов. План добавляет
`tokenId`+`lexemeKey` *поверх* индексов, не убирая индексы → дублирование и
неоднозначность «кто авторитет».

В greenfield надо **заякорить выравнивание устойчиво**:
- **греческая сторона:** только `tokenId` (стабильный ID MACULA). Индекс `g`
  убрать.
- **русская сторона:** `r` как индекс в `text.split()` устойчив, только если
  токенизация *заморожена*. §7.5 это разрушает фразой «words may be omitted and
  regenerated by the same deterministic tokenizer at runtime». **Убрать опцию
  ре-токенизации в рантайме.** Либо (а) `words[]` — замороженный
  закоммиченный авторитет, рантайм его не пересчитывает; либо (б) якорь —
  символьный диапазон `[start,end]` в замороженном тексте стиха (переживает
  любой токенизатор, согласуется с тем, что matching и так regex-овый по
  `ruMatches`). Рекомендую (б) как более прочный; (а) — минимальный приемлемый.

### 3.3 Версификация не смоделирована в схемах

`pairsByRef["john 1:1"]` (§7.7) предполагает, что у перевода и оригинала **один
и тот же** `ref`. По факту они расходятся системно (проверено ранее, audit
2026-06-13):

- 8 книг / 17 «лишних» стихов в syn (TR-плюсы): Мф 17:21; 18:11; 23:14; Мк 7:16;
  9:44,46; 11:26; 15:28; Лк 17:36; 23:17; Ин 5:4; Деян 8:37; 15:34; 24:7; 28:29;
  Рим 14:24–26;
- grcOnly: 2Кор 11:33; Откр 12:18;
- Рим, доксология: в grc-источнике её нет вовсе — нужно зафиксировать издание;
- 2Кор 11:33 слито в syn 11:32 (дефект данных Синодала, не вариант);
- Comma Johanneum (1Ин 5:7): syn = полный TR, grc = краткий NA.

Схемы §7.5–7.7 не имеют полей для этого. Нужна **явная модель
verse-correspondence** в alignment-pack, например:

```json
"verses": {
  "1corinthians 11:33": { "syn": "11:32b", "grc": null, "status": "synOnly", "variant": "syn-merge" },
  "2corinthians 11:33": { "syn": null, "grc": "11:33", "status": "grcOnly" }
}
```

Без неё модель развалится на первом расхождении, а «orphan» русские слова из
TR-плюсов будут выглядеть как ошибки выравнивания (см. §4.2 про «100% explained»).

### 3.4 `hasAlignment` в языково-нейтральном ядре — самопротиворечие

§7.8: `hasAlignment` = «есть видимая `e`/`f` пара **в текущем дефолтном переводе**».
Это факт про *syn*-выравнивание, зашитый в нейтральный греческий core, что прямо
противоречит §4.1/§4.7 («core — language-neutral»). Для будущего BSB этот флаг,
посчитанный по syn, будет неверен. Вынести в производный per-alignment индекс
(`align/{alignmentId}/index.json`), а в core — не держать.

### 3.5 `refs[]` — размерная мина, которую генератор уже обходит

§7.8 предлагает `"refs": ["john 1:1","john 1:14","acts 6:2"]` (массив) в
`top1000.core`. Для частотных лемм это десятки тысяч записей (ὁ), λόγος — 318.
На 1000 лемм взорвёт бюджет «<1 MB» (§12). При этом **генератор уже хранит
`firstRef` (единственный)** (`assets/data/generated/macula/frequency.json`).
То есть §7.8 — регресс относительно того, что уже сделано правильно. Хранить
`firstRef` + `verseCount`; полный список занятий — только в canonical/audit, не
в рантайме.

### 3.6 Польза словаря: 80 % top-1000 без русского

Проверено: курировано **204** леммы, а top-1000 = 1000
(`assets/data/lexicon/frequency.json`). ~800 слов в офлайн-словаре будут без
русского глосса. «Словарь работает офлайн» (§15) структурно верно, но это и есть
вопрос «что нужно пользователю». Решение — см. §4.3.

## 4. Ответы на уточняющие вопросы → решения

### 4.1 Курируемый русский слой: **перенести и дополнить** (рекомендация)

Из трёх вариантов («перенести / перенести+дополнить / пересобрать») —
**перенести дословно как пол (floor), сверху дополнить под новую схему**.
Обоснование:

- `ruMatches` — самый дорогой и трудновоспроизводимый актив (выверенные регулярки
  с `ruExclude`: «слов(о|а|…)» но не «словно/словарь»). Пересобирать с нуля —
  выбросить выверенную работу и заново ловить ложные срабатывания.
- Но **схему надо эволюционировать**: текущая запись плоская
  (`id,lemma,translit,strong,gloss,pos,ruMatches,ruExclude,refs,allRefs,…`); в
  новой модели курируемые поля идут в `locale/ru/core.json` (match-rules) и
  `locale/ru/top1000.json` (глоссы), присоединяются к нейтральному ядру по
  `lexemeKey`.
- «Дополнить» = довести покрытие глоссов вверх по частоте (см. §4.3), не трогая
  выверенные 204.

То есть: миграция данных курации — **механический перенос полей по `lexemeKey`**
(не ручная пересборка), плюс отдельная задача расширения покрытия.

### 4.2 «100 % правильность выравнивания» — критический разбор

> **Зафиксировано (подтверждено заказчиком):** 100 % **coverage НЕ требуется**;
> обязательна 100 % **precision**. Дальнейшее — операционализация этой цели.

Здесь **обязательно развести два понятия**, иначе цель звучит недостижимо:

- **Точность (precision):** из *показанных* пар — 100 % верны.
  **Достижимо** механизмом fail-closed: всё неуверенное помечается `q=u` и
  **скрывается** (это уже заложено в §7.7). Это и есть правильное прочтение
  «правильности».
- **Полнота (coverage/recall):** каждое слово получает пару.
  **Недостижимо 100 %** на этой паре текстов: Синодальный основан на
  Textus Receptus/византийском, SBLGNT — критический текст. TR-плюсы (Comma
  Johanneum, доксология Мф 6:13b, synOnly-стихи из §3.3) **физически не имеют**
  греческого токена-соответствия. Симметрично — греческие частицы (μέν, δέ, γε…)
  и grcOnly-стихи не имеют русского слова.

**Прямое продуктовое следствие (принято):** 100 % precision ⟹ часть русских слов
останется **без греческой подсветки/замены** (fail-closed их прячет). Нельзя
одновременно «100 % верно» и «у каждого слова есть пара» — заказчик выбрал
правильность, coverage best-effort. Операционная формулировка цели (как в
`DEVELOPMENT_7.md`):

> **precision = 100 % на показанных парах** (fail-closed) **+ «100 % explained»:
> каждое непарное слово попадает в документированную категорию** (текстовый
> вариант / служебное слово / структурное несоответствие), а не в «ошибку».

Что это меняет в плане:

- Механизм перегенерации (Q2): алгоритм Strong+`ruMatches` от источника не
  зависит, но `tokenId` меняются → **перегенерация против MACULA обязательна в
  любом случае**. Это делается тем же конвейером, не «rebuild методологии».
- **Но** «100 % precision» нельзя *утверждать* — её можно только *измерить* на
  выборке. Значит часть «тяжёлой» верификации Phase 4 **оправдана** твоей целью,
  вопреки оценке feedback1 («academic overkill»). Конкретно нужны:
  1. инварианты (schema, bounds, нет дублей, детерминизм) — обязательно;
  2. **fail-closed** `q=u` скрыт — обязательно (даёт высокую precision ценой
     recall);
  3. **реестр текстовых вариантов** (`assets/data/textual-variants.json` уже
     есть) — чтобы orphan был «explained», а не «error»;
  4. **held-out выборка с ручной/слепой проверкой precision** — чтобы 100 %
     было *измерено*, а не объявлено.
  Чего НЕ нужно: гнаться за порогами recall и за «100 % coverage» — это
  противоречит цели и невозможно.

**Как 100 % precision обеспечивается на практике** (важно — это не одно и то же,
что «измерить precision»):

- **Структурно (даёт саму гарантию):** пара показывается, только если проходит
  строгие детерминированные критерии (совпадение Strong + срабатывание
  `ruMatches` + согласование признаков); всё, что не проходит, помечается `q=u`
  и **скрывается**. Precision на *показанном* множестве задаётся тем, насколько
  строг порог показа, а не статистикой.
- **Измеримо (даёт только границу, не доказательство):** held-out + слепая
  проверка дают оценку «0 ошибок на N показанных парах» → верхнюю границу частоты
  ошибок. **Доказать 0 ошибок на всех ~100k показанных парах нельзя.** Поэтому
  «100 % precision» = «строгий fail-closed порог, при котором на held-out
  ошибок не найдено», а не теорема. Это надо держать в голове: при находке
  редкой ошибки в проде реакция — *ужесточить порог показа* (сдвинуть пару в
  `q=u`), а не «терять» цель.

**Вывод по Q2:** не «полный rebuild с блокирующими recall-гейтами» и не «лёгкие
spot-checks». Среднее: **перегенерировать тем же алгоритмом против MACULA +
строгий fail-closed порог + held-out precision-аудит + реестр вариантов.**
Recall — best-effort (улучшается отдельным треком refine-passes, не блокирует
выпуск). Так «100 % правильность» = «100 % precision на показанном, всё
остальное — explained or hidden».

### 4.3 EN-глосс как fallback — принято, с оговоркой UX

Решение разумно и упрощает модель: `sourceGlosses.en` (= `glossesEn` в
генераторе) уже есть, показывать для ~800 некурируемых. Оговорки:

- Помечать явно как некурированный/машинный источник (не выдавать английское за
  русскую курацию).
- Для русскоязычного новичка голый английский глосс малополезен — добавить рядом
  **транслитерацию** (`translit` уже есть) и, по возможности, дешёвый русский
  под-глосс (см. §4.2 авто-RU как отдельный трек). Это «что нужно пользователю»:
  fallback должен быть понятен без знания английского.
- Граница чёткая: EN-глосс живёт в **нейтральном ядре** (`sourceGlosses`), а не в
  `locale/ru` — иначе нарушится §4.7.

### 4.4 Future-proof: id в схеме, файлов BSB/en — нет

Решение «разделить id, без файлов» — золотая середина, конкретизирую:

- **Оставить в схемах поля-идентификаторы** `translationId`, `originalId`,
  `alignmentId`, `localeId` — они дёшевы и предотвращают переделку. Каждая
  runtime-запись знает, к какому переводу/оригиналу/локали относится.
- **НЕ создавать сейчас** реестры `translations.json` / `originals.json` /
  `locales.json` и деревья `translations/bsb/**`, `lexicon/locales/en/**` (§5.3,
  §7.2–7.4). Для одного перевода + одной локали реестр из одной записи — лишняя
  косвенность. Достаточно констант в коде; реестр-файл вводится, когда появится
  второй перевод/локаль.
- Пути держать расширяемыми (`originals/sblgnt-macula/…`,
  `translations/syn/…`), чтобы добавление BSB было дописыванием, а не переделкой.

## 5. Проверенные факты (грунт для критики)

- `publicDir: 'assets'` (`vite.config.js:11`) → **всё** из `assets/` копируется в
  `dist/`. `globIgnores: ['**/data/generated/**']` (`vite.config.js:40`) убирает
  файлы только из **precache-манифеста Workbox**, не из копирования. Сейчас в
  `assets/data/generated/macula` лежит **369 MB** (`books` 200M, `tokens.jsonl`
  140M, `lexemes.json` 20M) — это уезжает в `dist/`. §4.4 плана прав; вынести
  canonical-слой из `assets/` — реальный приоритет, не теоретический.
- **Кразис — НЕ проблема модели** (поправка к моей же первой реакции): из 137 740
  токенов `strong[].length>1` — **0**; `+`-составной Strong — лишь **5**
  (ἐκπερισσῶς 1537+4053; ὑπερεκπερισσοῦ 5228+1537+4053; δισμυριάδες 1417+3461) —
  это одиночные леммы, уже покрытые §7.6. Значит «1 токен = 1 lexemeKey»
  **держится** — это плюс плана.
- **top-1000 не доминируется служебными** — `isFunctionWord` стоит лишь у **72**
  из 1000. Аргумент «словарь забит артиклями» снимаю.
- Генератор уже близок к `top1000.core` (§7.8): `frequency.json` имеет
  `rank,denseRank,lexemeId,lemma,tokenCount,verseCount,coverage,strong,pos,`
  `isFunctionWord,glossesEn,transliteration,firstRef`. Не хватает: маппинг
  `lexemeKey`, `forms[]`, `domains[]`, `hasAlignment` (последний — вынести из
  core, §3.4).

## 6. Что в плане хорошо (сохранить)

1. `lexemeKey` как стабильный app-ключ; MACULA-хеши — только provenance.
2. MACULA = источник истины для греческого, не для русского UX (§4.1).
3. fail-closed на неуверенном выравнивании, `q ∈ {e,f,u}`, `u` скрыт (§7.7) —
   именно это обеспечивает твою «100 % правильность» (§4.2).
4. `localeId` ≠ `translationId` (§6.8) — правильная развязка.
5. source-манифесты с SHA-256 и лицензиями (§5.1) — критично для чистоты.
6. Компактные рантайм-паки отдельно от verbose-canonical (§4.3) — верно, но без

## 9. Отчёт о сомнениях

1. **«100 % правильность» — РЕШЕНО (подтверждено заказчиком):** coverage 100 %
   НЕ требуется; обязательна 100 % precision = строгий fail-closed порог + «100 %
   explained» для непарного (§4.2). Остаточное сомнение лишь в формулировке:
   100 % precision — это *структурная гарантия порога показа*, измеримая на
   held-out только как граница, а не доказуемая на всех ~100k парах. При находке
   редкой ошибки реакция — ужесточить порог (сдвинуть в `q=u`), а не считать цель
   проваленной.
2. Не проверял **коллизии транслитерации** между *разными* леммами (лемма↔lexemeId
   чисто 1:1, но `translit` двух разных лемм может совпасть). От этого зависит,
   нужен ли хвост-дизамбигуатор в `lexemeKey` (§3.1) — рекомендую нужен, но не
   измерил частоту коллизий.
3. **369 MB → `dist/`**: вывод сделан из `vite.config.js` (publicDir + globIgnores
   = только precache). Не проверял реальной сборкой `npm run build`, копируется ли
   `generated/` в `dist/` фактически (есть `runtimeCaching` на
   `/data/generated/macula/` — возможно, рантайм сейчас *читает* оттуда; тогда
   вынос потребует и правки загрузчиков). Подтвердить сборкой.
4. **Символьный якорь для русского** (§3.2) прочнее индекса, но требует, чтобы
   движок (`form-layer.js`, `reading.js`) умел заменять по диапазону, а не по
   индексу слова — не оценивал объём этой правки в коде. «Замороженный `words[]`»
   — дешевле, но менее устойчив. Решение за тобой.
5. **`morphology.labelRu`** имеет известные дефекты (наклонение `D` не
   раскодировано; 1-е лицо местоимений теряется — из feedback1 §3,10). На модель
   данных не влияет, но если рантайм берёт `labelRu` напрямую — починить декодер
   до выпуска. Не перепроверял на текущем генераторе.
6. **Издание grc-источника для Римлян** (пропавшая доксология) — открытый вопрос
   из audit 2026-06-13; влияет на verse-correspondence (§3.3). При переходе на
   MACULA SBLGNT может закрыться сам, но это надо подтвердить на сгенерированных
   паках, а не предполагать.
7. **Покрытие top-1000 русскими глоссами «вверх по частоте»** (§4.1 «дополнить»)
   — не оценивал, сколько из 204 курируемых попадают в top-1000, а сколько top-1000
   остаются без пары. От этого зависит реальный объём ручной доработки.
