## 1. Контекст

### 1.1. Что есть сейчас

Приложение — PWA для чтения греческого Нового Завета. Текущее состояние:

- **UI полностью на русском.** Все строки (~200+) жёстко зашиты в 15+ JS-файлах:
  заголовки, кнопки, aria-label, плейсхолдеры, сообщения об ошибках — всё
  прописано строковыми литералами в `innerHTML` / `textContent`.

- **Никакой i18n-инфраструктуры нет.** Нет ни словарей переводов, ни функции
  `t()`, ни языкового параметра в настройках.

- **Исходный текст чтения — английский (BSB).** Это осознанный компромисс ради
  чистой лицензии (public domain). Русский перевод вернётся отдельным этапом
  после решения лицензионного вопроса — [PROJECT.md §7](PROJECT.md).

- **Язык UI зафиксирован как архитектурное решение** — [PROJECT.md §3](PROJECT.md):
  «Язык UI — русский». Локализация расширяет это решение: UI становится
  переключаемым, а не только русским.

### 1.2. Зачем локализация

1. **Пользователи.** Приложение могут использовать люди, не владеющие русским —
   английский UI открывает доступ международной аудитории.
2. **Продуктовая цель.** PROJECT.md §7: «возврат русского перевода отдельным
   лицензионным этапом». Когда русский перевод вернётся, английский UI
   позволит пользователю выбрать: русский интерфейс с русским переводом, или
   английский интерфейс с английским переводом.
3. **Архитектурная чистота.** Локализация заставляет отделить данные от
   представления — это делает код поддерживаемее.

### 1.3. Отношение к Phase B

[Phase B](PHASE-B-MULTILANG-PATHS.md) — параметризация путей данных
(`bibles/{lang}/{translation}/`) для поддержки нескольких переводов —
делается **до** локализации.

| | Phase B | Локализация |
|---|---|---|
| Что меняет | Пути к файлам данных | Строки в UI |
| Настройки | `sourceLang`, `targetLang`, `translation` | `uiLang` |
| Данные | Структура каталогов `assets/data/` | `books.json` (+En поля), словари переводов |
| Зависимость | Независим | Использует инфраструктуру Phase B (settings, router) |

Фазы независимы архитектурно, но локализация идёт после — чтобы использовать
уже параметризованные настройки и роутер.

## 2. Сравнение подходов

Рассмотрены три подхода к реализации. Выбран подход C.

### Подход A: Минимальный — плоский `t()` + JSON-словари

Файлы `src/i18n/ru.json`, `src/i18n/en.json` с плоскими ключами. Функция
`t(key, lang)` — поиск по словарю. Ручная замена каждой строки в 15+ файлах.

| Плюсы | Минусы |
|---|---|
| Ноль зависимостей | Нет интерполяции `{{var}}` без самописного дополнения |
| Прозрачно, легко дебажить | Нет плюрализации |
| Минимум кода | Много ручной замены — каждая строка отдельно |

**Отклонён:** отсутствие интерполяции и плюрализации критично — в русском
языке множественные формы не сводятся к `'s'` на конце.

### Подход B: Библиотека i18next

Полноценный i18n-фреймворк: плюрализация, интерполяция, неймспейсы, детект
языка из коробки. Стандарт индустрии для React/Vue-проектов.

| Плюсы | Минусы |
|---|---|
| Батарейки в комплекте | +10KB gzip к бандлу |
| Стандарт, документация, сообщество | Странно смотрится в vanilla-JS проекте без фреймворка |
| Плюрализация для 200+ языков | Избыточен для ~200 строк — 90% возможностей не используются |
| | API библиотеки навязывает свою структуру (неймспейсы, бэкенды) |

**Отклонён:** приложение — чистый vanilla JS, без React/Vue. Тянуть
полноценный i18n-фреймворк ради 200 строк — перебор. Встроенный
`Intl.PluralRules` покрывает нужную плюрализацию без зависимостей.

### Подход C (выбран): Лёгкий самописный модуль + data-driven строки

Модуль `src/i18n/index.js` (~100 строк): класс `I18n` с `t(key, params?)`,
авто-детект из `navigator.language`, синхронизация с URL и settings.
Переводы — в JSON. Ключевая идея: **значительная часть «строк» уже лежит
в данных** и не требует перевода — только выбора правильного поля.

| Категория | Где уже есть данные для обоих языков |
|---|---|
| Названия книг | `books.json` — добавляются поля `shortEn`, `titleEn` |
| Словарные глоссы | `core.json` уже содержит `ruGloss` + `glossesBerean`/`glossesCherith` |
| Темы / контраст | Константы в `settings.js` → переезжают в JSON-словари |
| UI-хром | ~80 строк (заголовки, кнопки, aria-label) — ручной перенос в словари |

| Плюсы | Минусы |
|---|---|
| 0 зависимостей — только `Intl.PluralRules` (встроен в браузер) | Надо написать и поддерживать сам модуль |
| Data-driven строки не дублируются — язык меняет только источник данных | Нестандартное решение (но тривиальное для понимания) |
| Естественно ложится на URL-схему `#/ru/read/john` | |
| ~100 строк кода — легко прочитать и отладить | |
| Плюрализация через `Intl.PluralRules` — стандарт браузера | |

**Выбран** как оптимальный для масштаба проекта (vanilla JS, ~200 строк,
2 языка) и архитектурно соответствующий data-driven природе приложения.

## 3. Архитектура

### 3.1. Модуль `src/i18n/`

```
src/i18n/
├── index.js      # I18n-класс + singleton export (~100 строк)
├── ru.json       # Русский словарь (~120 ключей)
└── en.json       # Английский словарь (~120 ключей)
```

**API класса `I18n`:**

| Метод | Назначение |
|---|---|
| `init(store, settings) → lang` | Детект языка, загрузка переводов, подписка на store |
| `t(key, params?) → string` | Перевод с `{{var}}`-интерполяцией и плюрализацией |
| `get lang()` | Текущий язык (`'ru'` \| `'en'`) |
| `setLang(lang)` | Сменить язык, загрузить переводы |
| `detectBrowserLang() → lang` | `navigator.language` → `'ru'` \| `'en'` |
| `langFromPath(path) → lang\|null` | Извлечь язык из URL |
| `langPrefix(lang?) → string` | Вернуть `'/ru'` или `'/en'` |
| `bookName(book) → {short, title}` | Название книги на текущем языке |
| `gloss(lexeme) → string\|null` | Глосса леммы на текущем языке |
| `themeLabel(slug) → string` | Метка темы (`'Пергамент'` / `'Parchment'`) |
| `contrastLabel(level) → string` | Метка контраста (`'Чёткий'` / `'Sharp'`) |
| `destroy()` | Отписка от store |

### 3.2. Схема URL

```
Было:                       Стало:
#/read/john                 #/ru/read/john
#/dictionary                #/ru/dictionary
#/settings                  #/ru/settings
```

Языковой префикс `ru` / `en` — первый сегмент после `#/`. Обратная
совместимость: старые URL без префикса редиректятся с авто-детектом языка.

### 3.3. Поток при старте

```
1. app.js: loadSettings()
2. app.js: applyTheme(), applyContrast()
3. app.js: i18n.init(store, settings)
   ├── lang = settings.uiLang || detectBrowserLang()
   ├── _loadTranslations(lang)      // import('./ru.json')
   ├── subscribe to store.settings  // реакция на смену uiLang
   └── if uiLang was null → persist
4. app.js: handleRoute(parse(location.hash))
   ├── if old URL (no lang prefix) → redirect to #/{lang}/...
   └── else → switchScreen(screen, params)
5. Все экраны: i18n.t('key') → строки на правильном языке
```

### 3.4. Плюрализация

Использует `Intl.PluralRules` — встроенный API браузера, без зависимостей.

```json
// ru.json — русская (one / few / many)
"dict.wordsCount": {
  "one":  "{{count}} слово",
  "few":  "{{count}} слова",
  "many": "{{count}} слов"
}

// en.json — английская (one / other)
"dict.wordsCount": {
  "one":   "{{count}} word",
  "other": "{{count}} words"
}
```

Логика в `t()`: если значение — объект с ключами `one`/`few`/`many`/`other`,
выбирается по `Intl.PluralRules(lang).select(count)` и интерполируется `{{count}}`.

### 3.5. Data-driven строки

**Книги** — `books.json` получает параллельные поля:
```json
{ "id": "john", "short": "Ин", "title": "От Иоанна...",
  "shortEn": "Jn", "titleEn": "John", "chapters": 21 }
```
Хелпер `i18n.bookName(book)` возвращает `{short, title}` на текущем языке.

**Глоссы** — `core.json` уже содержит двуязычные данные:
- `ruGloss` — русский глосс (сейчас используется везде)
- `glossesBerean` / `glossesCherith` — английские глоссы

Хелпер `i18n.gloss(lexeme)` выбирает поле по языку: `ru` → `ruGloss`,
`en` → `glossesBerean[0]` с fallback на `ruGloss`.

**Темы / контраст** — константы `THEME_LABELS` и `CONTRAST_LABELS` удаляются
из `settings.js`. Их значения — в JSON-словарях (`theme.*`, `contrast.*`).
Хелперы: `i18n.themeLabel(slug)`, `i18n.contrastLabel(level)`.

## 4. План реализации

14 задач, от фундамента до финального гейта. Оценка: ~180 новых строк кода,

**Создать:** `src/i18n/index.js`, `src/i18n/ru.json`

## 5. Что НЕ входит

- ❌ Перевод греческих морфологических меток (N-NSM, V-PAI-3S) — это коды
- ❌ Перевод данных `lexicon/core.json` и `dictionary.json` — уже содержат оба языка
- ❌ Перевод `alphabet.json` — имена букв интернациональны
- ❌ Изменение IndexedDB, PWA-кешей, схем данных
- ❌ Добавление второго перевода (русского) — это Этап В после Phase B
- ❌ Перевод `data-manifest.json`, `build-report.json` — машинные данные

## 6. Риски

| Риск | Вероятность | Смягчение |
|---|---|---|
| Статические импорты JSON не работают в production-сборке Vite | Низкая | Vite поддерживает `import('./foo.json')` из коробки; проверено на `npm run build` |
| Старые URL без префикса ломают навигацию | Низкая | Обратная совместимость: старые паттерны в роутере + редирект в `handleRoute` |
| IndexedDB-настройки без `uiLang` у существующих пользователей | Низкая | `null` = авто-детект, идемпотентно при первом запуске |
| Переключение языка не обновляет текст на лету | Средняя | `navigate()` с тем же экраном → unmount/mount → новый `i18n.t()` |
| Рассинхрон `books.json` source vs output при обогащении скриптом сборки | Низкая | Скрипт копирует ВСЕ поля из source + добавляет вычисляемые; английские поля проходят насквозь |
